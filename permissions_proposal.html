Frontify permissions: today and proposed

Every library is set up slightly differently today. One group-based model, applied the same way everywhere, would make access predictable, easier to audit and easier to run.

How to read this. Frontify's API doesn't say which groups were given access to a library, so group access is inferred from group membership and each user's role. Individual users are counted, not named. The API also has no folder permissions, so folder-level exceptions set in the Frontify UI are not shown. Check before changing anything.

Owners and Editors per library

Today the number of Owners ranges widely between libraries. In the proposal, every library has the same Owners (the platform admin group) and the same Editors (the Brand team).

What we found

Six observations from the data on the 10 libraries.

Proposed model: 5 groups, 3 roles, the same in every library

Access is only ever given to groups. Changing someone's access means changing their group membership, never the library settings.

Groups, not people

No individual role assignments. Joining or leaving a group is the only way to change access, which keeps it auditable.

Same model everywhere

All 10 libraries share one set-up, so a new library is configured in minutes and nobody has to check library by library.

Least privilege

Owner (library settings and members) only for platform admins. Editor for people who manage assets. Viewer for everyone else, including integrations.

What changes

Steps to get from today's set-up to the proposed model, and how many people each one affects.

Folders

Folders inherit their library's access. The API has no folder permissions, so check the larger trees in the Frontify UI for folder-level exceptions. Proposed rule: no folder-level exceptions; content that needs a different audience gets its own library.
